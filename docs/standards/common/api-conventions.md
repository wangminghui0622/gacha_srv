# API 接口约定（前后端共同遵守）

> 本文件统一了参考项目中的分歧写法：分页字段统一为 `page`/`pageSize`（不再使用 `List` 作页大小）。

## 响应信封

1. 所有 HTTP 接口返回：

```json
{ "code": 0, "msg": "success", "data": { } }
```

2. `code == 0` 表示成功；非 0 时 `msg` 为面向用户的中文错误描述，`data` 省略（`omitempty`）。
3. HTTP 状态码恒为 200，错误只通过 `code` 表达（由网关 `SetOkHandler` / `SetErrorHandlerCtx` 统一处理，业务代码不得自行拼信封）。
4. 分页响应固定结构：`{ "list": [...], "total": 100 }`；分页请求参数 `page`（默认 1）与 `pageSize`（服务端上限，如 50）。

## 错误码分段

5. 全平台唯一编码规则（详见 `../backend/05-errors.md`）：

| 段 | 含义 |
|----|------|
| `0` | 成功 |
| `400/401/403/404/408/429/500` | HTTP 语义错误（参数/鉴权/限流/服务端） |
| `600-699` | 基础设施（DB 600、DB 重复 601、Redis 610、DTM 630……） |
| `1000-1999` | 用户域（用户服务） |
| `2000-2999` | 抽奖域（抽奖服务） |
| `3000-3999` | 玩法域（玩法服务） |
| `4000-4999` | 商城域（商城服务） |
| `5000-5999` | 基础域（基础服务） |
| `6000-6999` | 第三方域（第三方服务） |
| `7000-7999` | 运营域（运营服务） |
| `8000-8999` | 支付域（支付服务） |

6. 新增业务域时先在本表登记千位段，再定义具体错误码；一个码只表达一种错误，禁止复用。

## 路由与命名

7. 网关路由前缀统一 `/gacha/api/v1`；路径 kebab-case（`/user/bind-pix`、`/games/records`）。
8. HTTP 动词：查询 `get`、创建 `post`、更新 `put`；写操作不接受 query 参数传数据。
9. 字段命名 camelCase（JSON、`.api`、`.proto` 三者一致）；时间字符串 `"2006-01-02 15:04:05"`；金额一律字符串两位小数（如 `"100.50"`），禁止 float。
10. 请求参数校验：必填/长度/格式用校验 tag（`validate:"required,min=6,max=32"`），网关统一返回 400 与中文错误信息；逻辑层不重复做格式校验。

## 鉴权

11. 客户端在 `Authorization: Bearer <token>` 携带令牌；网关中间件校验后把用户身份放入上下文（`userId`），logic 从上下文读取。
12. 公开接口（登录、注册、公告、支付回调等）在 `.api` 的 `@server` 块中不挂 `middleware: JwtAuth`。
13. 支付回调等第三方接口必须验签（密钥只存配置，且为占位符）。

## 分页与列表

14. 列表接口必须分页，禁止一次返回全量；列表字段命名复数（`games`、`channels`）或统一 `list`。

## 前端对接

15. 前端 services 层复用同一信封类型 `ApiResponse<T> = { code, msg, data }`，`code !== 0` 或 HTTP 401 时统一处理（清 token、跳登录），见 `../frontend/05-api-layer.md`。
